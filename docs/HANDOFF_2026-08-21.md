## What happened: path 1 was executed

The prior handoff left an open decision — train IPPO against the corrected
`green_wave`/`max_pressure` bar and report the result either way, find a
demand scenario a fixed plan can't serve, or stop and consolidate the
single-intersection thesis. **Path 1 was chosen and run to completion.**

**Result: IPPO loses.** Full detail, tables, and raw data pointers in
`docs/FINDINGS_2026-08-18-sp4-ippo-vs-corrected-bar.md` — read that before
touching anything corridor-RL related. Summary:

- At the properly-sized 16,000-step training budget: IPPO loses to
  `green_wave` by +22s (delay per completed trip), 0/10 seeds, on both
  `corridor_peak` and `corridor_tidal` — worse even than the reactive
  `max_pressure` baseline.
- A budget-sensitivity check (3 seeds, 100,000 steps — matching the budget
  the single-intersection sanity check used) cut that gap by ~79%, to
  +4.4s, but did not close it. All 3 confirmatory seeds still lose.
- `ppo_core` (the hand-rolled PPO) is validated against SB3 PPO at matched
  hyperparameters and both budgets — near-parity both times, so the loss is
  not an implementation bug.
- A second demand structure, `corridor_skew` (uneven cross-street load,
  same total demand as `corridor_peak`), was added and calibrated mid-run
  to test a second adaptation hypothesis. It didn't change the picture
  either — its own documented flaw is that 600 veh/h at one node never
  approaches the ~1800 veh/h capacity the shared phase split leaves
  available, so the mechanism it was built to expose never actually costs
  anything. IPPO was never trained on it (the reference calibration alone
  was enough to show it wasn't worth the compute).

**The recommendation in the findings doc: consolidate.** This result plus
the single-intersection one (`docs/FINDINGS_2026-08-12.md`) is now a
twice-replicated finding at two different network scales — "a
competently-timed fixed plan beats both reactive and learned control." That
is the corridor project's actual output at this point, not a stepping stone
to something else.

## What's still open, if anyone wants to keep pushing (not recommended by default)

From the findings doc's own "What this doesn't answer":

1. Only 3 of 10 seeds, only `corridor_peak`, were re-checked at 100k steps.
   A full 10-seed, both-scenario run at 100k+ would firm up the exact
   remaining gap, though the trend (79% closed, not asymptoting to zero)
   makes a reversal unlikely.
2. IPPO's hyperparameters are still the reused single-intersection tuning
   (SP2's disclosed limitation) — never re-tuned for the corridor's 3-agent,
   pooled-buffer setting. Untested whether that would move the ~4.4s gap.
3. A redesigned `corridor_skew` that actually pushes a node's cross demand
   near/above its phase-split-constrained capacity (the same saturation-math
   discipline `corridor_tidal` used, which `corridor_skew` skipped) might
   still find real room for adaptive control — this one didn't test that
   harder version.
4. The mid-episode incident/blockage scenario (prior handoff's path 2,
   second half) was never designed or built.

## How this session ran, if it matters to you

Entirely on this machine (an M1 Max, 10 cores, 32GB) with no cloud
involvement, executed via `superpowers:subagent-driven-development` off
`docs/superpowers/plans/2026-08-18-sp4-ippo-corridor-training.md` (7 tasks,

`corridor_skew`, and the budget-sensitivity check). One operational note
worth knowing if you run long training here again: this sandbox's
`caffeinate -i` prevents *idle* system sleep but not *lid-close* sleep —
closing the lid on battery with no external display will pause any running
background job (safely — processes resume, nothing is lost — but wall-clock
inflates by however long it's closed). Not a code concern, just a "why did
this take way longer than estimated" answer if it comes up again.
