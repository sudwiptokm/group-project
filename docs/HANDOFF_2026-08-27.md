## What happened, in order

### SP13 -> SP13b: is the green_wave failure band a property of ratio, or of span?

SP13 (`docs/FINDINGS_2026-08-26-sp13-geometry-dose-response.md`) swept
asymmetry ratio `r` at fixed span=400 and found green_wave fails only in a
bounded band `r ~ [0.51, 0.80]`, recovering on both sides — overturning
SP10's "3/3 generalizes" monotonic reading. It flagged span as an unresolved
confound: SP8/SP10's original irregular nets sat at span=700, off that axis.

SP13b (`docs/FINDINGS_2026-08-27-sp13b-span700-confound.md`) reran the same
8-point ratio sweep at span=700
(`analysis/build_geometry_sweep_nets_span700.py`,
`analysis/geometry_sweep_span700.py`, zero-shot only, no new training).
**Result: the band's shape is NOT ratio-only.** span=700 has 3 crossings
(r~0.572, 0.750, 0.842), not span=400's 1; the r=0.50 baseline is already
3.26s slower than span=400's; and green_wave does not recover at r=0.90 the
way span=400 does. idqn stays flat (<1.3s band) at both spans.

### SP14 -> SP14b: does the lambda=0.25-vs-0.5 gap survive n=3 -> n=10?

SP14 (`docs/FINDINGS_2026-08-26-sp14-lambda-ablation.md`) found lambda=0.25
beats the project's lambda=0.5 default on delay on both geometries, at n=3
seeds — but flagged the irregular-net gap (0.25s) as thin relative to this
project's typical seed noise.

SP14b (`docs/FINDINGS_2026-08-27-sp14b-lambda-n10.md`) trained the 7 missing
seeds (45-51) for lambda in {0.25, 0.5} only (`analysis/lambda_ablation_n10.py`,
reusing `analysis.lambda_ablation`'s own eval code) and re-evaluated zero-shot.
**Result: the gap did not shrink, it grew** — irregular 0.245s -> 0.593s (9/10
seeds agree), regular 0.874s -> 0.997s (10/10 agree). Not an n=3 artifact.

### SP15 -> SP15b: does retuning HPs for MAPPO's wider critic close the gap to IPPO?

SP15 (`docs/FINDINGS_2026-08-27-sp15-mappo-smoke.md`) ported MAPPO (SP3,
previously stale-branch-only) onto current `train_corridor.py` and found it
underperforms IPPO at n=1 seed on both geometries — but PPO's HPs were the
project's single-intersection-tuned defaults, never retuned for MAPPO's
57-dim joint critic (vs IPPO's 19-dim local one), a live confound.

SP15b (`docs/FINDINGS_2026-08-27-sp15b-mappo-retune.md`) tried 3 cheap manual
HP variants (`analysis/mappo_retune_smoke.py`: lr/5, batch_size x2, hidden
(512,512) — `train_corridor.train()`/`evaluate()` gained backward-compatible
`hp_overrides`/`tag_suffix` params for this). **Result: best variant
(wide512) narrows the regular-net gap 61% (+1.35s -> +0.53s) but none beat
IPPO on either geometry; lr_low collapses training entirely (+10s worse).**

**Final call: MAPPO stops here, does not escalate to full n=10 rigor.**
Stated in SP15b's own Recommendation section — this project's convention is
each FINDINGS doc carries its own verdict, no separate index file exists.

### SP13b -> SP13c: does the crossing count move monotonically with span, or jump?

SP13c (`docs/FINDINGS_2026-08-27-sp13c-span550.md`) added a third span point,
550m (midpoint of SP13's 400 and SP13b's 700), reusing the same 8-ratio sweep
(`analysis/build_geometry_sweep_nets_span550.py`,
`analysis/geometry_sweep_span550.py`, zero-shot only, no new training).
**Result: not gradual — the 1-crossing-to-3-crossing transition already
happened by span=550.** Three crossings (r~0.584, 0.755, 0.897), close to
span=700's own locations (0.572, 0.750, 0.842), not intermediate toward
span=400's single band. Also found a genuine anomaly: span=550's r=0.50
baseline (23.15s) is *higher* than both span=400's (13.46s) and span=700's
(16.72s) — not a monotonic function of span — unexplained by either prior
doc's proposed mechanism.

Same doc's addendum inspected `corridor_control`'s offset/quantization
schedule as a candidate explanation for that anomaly and **ruled it out**:
worked through the exact travel-time offsets, the 5s decision-grid
quantization delay, and the edge-length-vs-node-distance gap for all three
spans' r=0.50 nets — all three predict span=550 should be the *best*-aligned
of the three (least quantization delay, 98.7%/97.3% platoon/green overlap
vs span=700's 68%/69%), the opposite of the observed ranking. tripinfo
`timeLoss` distributions also confirm it's a uniform per-trip effect, not
rare gridlock outliers. The real cause is still open — likely emergent SUMO
car-following/queueing dynamics the deterministic control layer doesn't
model — and would need a trajectory or queue-length timeseries comparison to
pin down, not more schedule math.

A second addendum followed that suggestion:
`analysis/queue_timeseries_span_compare.py` recorded per-signal queue
(halting count) and phase over a full episode for green_wave on the three
r=0.50 nets. **Localized the anomaly to C3 specifically** — C1 and C2's
queues are essentially span-invariant, but C3's incoming-arterial halting
count is 2.50 mean/14 max at span=550 vs 0.10-0.21 mean/3-5 max at span=400/
700, and 27.5% of steps have ≥5 vehicles halted vs ~0%. Ruled out downstream
spillback (C3_E shows zero halting at all three spans) and ruled out a
phase-index/semantics bug (C3's raw `tlLogic` phase state strings are
byte-identical across all three net files). The queue is elevated
specifically during C3's own nominal green phase, not red — consistent with
a late-starting-green backlog that never fully clears each cycle, but not
confirmed; the precise mechanism needs per-cycle trace data at C3, not
attempted.

### SP13c -> SP13d: does a fourth span point confirm the transition is bracketed, or break the story?

SP13d (`docs/FINDINGS_2026-08-27-sp13d-span450.md`) added a fourth span
point, 450m (near the low end of SP13c's (400m, 550m] bracket), same 8-ratio
sweep, zero-shot only. **Result: breaks the bracketing story entirely.**
span=450 shows *zero* crossings — idqn ahead at every single ratio point,
0.50 through 0.90, gap shrinking smoothly with no sign change. The sequence
across span is now **1 → 0 → 3 → 3** (400/450/550/700) — not a single
transition point anywhere, at least two regime boundaries between 400m and
550m.

Bigger result at the time: **max_pressure spikes almost identically to
green_wave at span=450/550's r=0.50** in aggregate delay/trip (max_pressure:
25.83s/28.48s/23.48s/22.05s at span=400/450/550/700, tracking green_wave's
13.46s/28.36s/23.15s/16.72s) while idqn stays flat (16.56s-19.56s). This
initially read as a shared capacity/geometry effect any non-learning
controller struggles with — but SP13d's own addendum (below) then pointed
the queue instrumentation at max_pressure directly and found that reading
doesn't hold up.

**Addendum, same doc**: ran `analysis/queue_timeseries_span_compare.py`
against max_pressure across all four spans. **The "shared mechanism" story
does not survive contact with the per-signal data.** green_wave's C3 queue
is worst exactly at spans 450/550 (mean 2.71/2.50) and clean at 400/700
(0.21/0.10) — consistent with one localized story. max_pressure's C3 queue
does *not* match: substantial at 400/450/700 (mean 2.02/1.47/1.13) but its
*best* point is span=550 (0.12, essentially clean) — the exact span where
green_wave's C3 problem is worst. max_pressure's own elevated signal at
span=550 is C2, not C3. So the two controllers' aggregate delay numbers
happen to move together at spans 450/550, but their actual congestion is not
co-located — either coincidental independent struggles, or a shared
geometry-driven cause whose effect lands on a different signal depending on
each controller's own reactive/fixed behavior. SP13c's offset-schedule
ruling-out and C3-localization-for-green_wave findings still stand as
descriptions of green_wave specifically; the "it's not green-wave-specific"
conclusion drawn from aggregate numbers alone was premature, and root cause
is now more open than either SP13c or SP13d's main section suggested.

### SP13 -> SP13e: does the failure band mirror onto r<0.50 (short block first)?

SP13e (`docs/FINDINGS_2026-08-27-sp13e-lowr.md`) swept r=0.10 through 0.45
at span=400 (SP13's original axis), filling the r<0.50 gap every doc in this
series had flagged. **Result: a second bounded band exists, but it's not a
mirror of the first.** Two crossings, r≈0.103 and r≈0.341 — idqn ahead
inside that band, green_wave ahead outside it. Reflecting SP13's original
[0.51, 0.80] band about r=0.50 would predict a low-r band at [0.20, 0.49];
the actual band [0.103, 0.341] only partially overlaps that prediction and
is shifted toward the extreme — block order (short block near the entry
signal C1 vs. near the exit signal C3) is a real variable, not just a
labeling convention. idqn stays flat (16.56s-17.87s) here too, a fourth
independent confirmation of its geometry-invariance. Also: max_pressure
moves in the *opposite* direction from green_wave across this range (its
delay drops through the r=0.20-0.30 middle, green_wave's peaks there) —
another instance of the two baselines not sharing a mechanism, consistent
with SP13d's addendum.

## What's actually still open (real gaps, not busywork)

- **The crossing-count-vs-span function is not bracketed or monotonic at
  all.** 1 → 0 → 3 → 3 across span=400/450/550/700 means at least two regime
  boundaries exist between 400m and 550m alone. More span points in that
  range (e.g. 420m, 480m, 500m) are needed to find them, not just one more —
  SP13d's own follow-up.
- **The r=0.50 spike's root cause is now more open, not less.** green_wave's
  own problem is confirmed localized to C3 (SP13c), with its offset schedule
  ruled out as the cause. max_pressure is also elevated in aggregate at
  spans 450/550 but its congestion sits on a *different* signal (C2 at
  span=550, not C3 — and its own C3 is actually cleanest exactly there),
  ruling out a single shared C3-level mechanism (SP13d's addendum). Neither
  controller's actual bottleneck at these spans has a confirmed cause; only
  green_wave's has even been localized to a specific signal.
- **Nobody has inspected what idqn's trained policy does differently at C3
  (or wherever) that keeps it immune** at every span/ratio sampled so far.
- **r<0.50 (short block first) is now tested at span=400 only** (SP13e: a
  second bounded band, r≈[0.103, 0.341], not a mirror of SP13's [0.51,
  0.80]). Still completely untested at spans 450, 550, 700 — where the
  high-r crossing count is already known to behave unpredictably
  (1→0→3→3), so nothing about span=400's low-r band should be assumed to
  generalize.
- **SP15b's own follow-up**: a real HP search (Optuna-style, joint over
  lr/hidden/batch) was never run for MAPPO — 3 hand-picked points is not a
  search, and `lr_low`'s collapse shows the space is sensitive. A
  genuinely-competitive-with-ippo MAPPO config has not been ruled out, only
  not found in this bounded attempt.
- **idqn checkpoints are n=3 everywhere in the geometry sweeps** (SP13,
  SP13b) — SP5's original constraint, no seeds beyond 42-44 exist for
  non-default lambda/geometry combos without new training.
- **HPs held fixed across every lambda arm** (SP14/SP14b) — the lambda=0.25
  optimum is relative to HPs selected at lambda=0.5, not independently
  retuned per lambda.
- No sub-project currently has open compute running. Everything either
  finished and is written up, or is a disclosed limitation in its own doc's
  "What this doesn't answer" section.

## Reproducing / picking this back up

Findings docs are self-contained; read the one for whichever thread you're
continuing. Key scripts if re-running or extending:

```bash
# SP13/SP13b geometry sweeps (zero-shot, no training needed if checkpoints exist)
python -m analysis.build_geometry_sweep_nets          # span=400 nets
python -m analysis.build_geometry_sweep_nets_span700   # span=700 nets
python -m analysis.geometry_sweep                      # span=400 sweep
python -m analysis.geometry_sweep_span700               # span=700 sweep

# SP14/SP14b lambda ablation
./run_lambda_ablation.sh                                # trains missing (lambda, seed) checkpoints
python -m analysis.lambda_ablation                      # n=3 report (lambda in {0,0.25,0.5,0.75,1.0})
python -m analysis.lambda_ablation_n10                  # n=10 report (lambda in {0.25, 0.5} only)

# SP15/SP15b MAPPO
python -m analysis.mappo_retune_smoke                   # 3 HP variants vs ippo/mappo baselines
```

All scripts are resumable (checkpoint/eval-CSV existence checks) — an
interrupted run costs at most the one in-flight job, not the batch. Expect
each `train_corridor_dqn.py` corridor_peak/100k-step run to take ~1-2.5h wall
clock alone, or 2-3h+ with 6-way parallelism contention on a 10-core machine
— plan background/overnight runs accordingly.
